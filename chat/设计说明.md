# 项目设计说明

## 1. 项目概述

本项目是一个轻量级多人聊天室，使用 JavaScript 完成前后端开发，通过 WebSocket 实现客户端与服务器之间的实时双向通信，并使用 SQLite 持久化保存聊天记录。

项目主要实现了多房间聊天、昵称设置、实时消息广播、历史消息恢复，以及**发送图片后自动调用 YOLO 做目标检测**。

---

## 2. 整体架构

项目主要分为前端、Node.js 后端、SQLite 数据库和 Python 检测进程四个部分。

```text
浏览器前端
    │
    ├── WebSocket ──────► 消息收发（文本 / 图片消息 / 检测结果）
    │
    ├── HTTP POST ──────► 上传图片本体
    │
    └── HTTP GET ───────► 读取图片（原图 + 标注图）
                              │
                              ▼
                        Node.js 后端
                              │
                              ├── 内存：在线用户、房间、WebSocket 连接
                              │
                              ├── SQLite：历史聊天记录
                              │
                              └── stdin/stdout（一行一个 JSON）
                                      │
                                      ▼
                              Python 常驻检测进程
                              （ultralytics / YOLO，模型只加载一次）
```

前端主要负责用户交互、选图/发图、消息展示以及接收消息后的页面显示。

后端负责房间管理、在线用户管理、WebSocket 通信、消息广播、图片存取、数据库操作，以及调用 Python 做检测。

Python 进程负责加载 YOLO 权重、执行推理、画出标注图。

SQLite 负责持久化保存聊天记录。

---

## 3. 数据存储设计

聊天消息保存在 SQLite 数据库中，消息表包含 `id`、`room`、`nickname`、`content`、`type`、`created_at` 等字段。

其中 `id` 为自增主键，用于唯一标识消息，同时可以根据 ID 判断消息在数据库中的先后顺序。

`type` 字段用于区分三种消息（这是在加图片功能时新增的）：

| type | 含义 | content 的格式 |
| --- | --- | --- |
| `text` | 普通文本 | 纯文本，直接显示 |
| `image` | 用户发的图片 | JSON：图片地址、文件名、大小、检测状态 |
| `yolo` | YOLO 检测结果 | JSON：标注图地址、结果摘要、检测明细 |

**为什么把 JSON 存进 content 而不是拆成多个字段**：

这样只需要给老表加一个 `type` 列就能完成升级，老的文本消息完全不受影响（`type` 默认就是 `text`），
不用重建表、不用写数据迁移脚本。代价是查询时不能在 SQL 里按图片字段筛选，
但当前所有查询都是「按房间按 id 查」，用不到这些字段，所以这个代价可以接受。

数据库升级是这样做的：先 `PRAGMA table_info` 检查 `type` 列是否存在，不存在才 `ALTER TABLE` 添加。
这样做是因为 `ALTER TABLE ADD COLUMN` 重复执行会直接报错，必须自己判断一次，
否则每次启动都会崩。

当前在线用户、房间状态以及 WebSocket 连接等实时状态保存在 Node.js 运行时内存中。

这样设计是因为在线用户和 WebSocket 连接属于实时状态，不需要永久保存，而聊天记录需要在页面刷新、重新连接甚至服务器重启后继续存在，因此使用 SQLite 进行持久化。

图片文件本身不存进数据库，而是以文件形式放在 `uploads/` 目录下：
原始图在 `uploads/original/`，标注图在 `uploads/annotated/`，数据库里只存文件名和访问路径。
这样做是因为数据库适合存结构化数据，把几百 KB 到几 MB 的二进制图片塞进去会让数据库迅速膨胀，
备份和查询都会变慢；而且图片本来就可以通过 URL 让浏览器直接缓存。

---

## 4. 用户加入房间

用户进入聊天室后首先设置昵称，然后选择并加入房间。

服务器会将用户以及对应的 WebSocket 连接记录到当前房间的在线用户集合中。

加入房间后，用户可以发送和接收该房间中的聊天消息。

---

## 5. 消息发送与广播

用户在前端输入消息后，前端将消息内容以及相关信息组织成 JSON，通过 WebSocket 发送给服务器。

服务器通过 WebSocket 的 `message` 事件接收客户端发送的数据，并解析 JSON。

消息经过服务器处理后，会被保存到 SQLite 数据库中，由数据库生成对应的自增 ID。

随后服务器根据消息所属的房间确定广播范围，并遍历该房间中的在线用户，通过对应的 WebSocket 连接将消息发送给客户端。

客户端收到服务器发送的消息后，通过 WebSocket 的消息事件进行处理，并更新聊天界面。

完整流程如下：

```text
用户输入
    ↓
前端组织 JSON
    ↓
WebSocket.send()
    ↓
Node.js 接收消息
    ↓
解析 JSON
    ↓
保存到 SQLite
    ↓
根据房间确定广播范围
    ↓
遍历房间内在线用户
    ↓
WebSocket.send()
    ↓
客户端接收消息
    ↓
更新聊天界面
```

---

## 6. 历史消息

聊天记录会持续保存在 SQLite 数据库中。

当用户加入房间时，服务器会查询该房间最近的 100 条消息。

查询时根据消息 ID 按降序获取最近的 100 条记录，然后将查询结果反转，使客户端最终按照消息的正常时间顺序显示。

因此，即使用户刷新页面、断开连接后重新加入房间，仍然可以从数据库中恢复之前的聊天记录。

图片消息恢复时，前端会根据保存的文件名重新拼出图片地址，
所以刷新页面后历史图片、包括 YOLO 的标注图，都会照常显示。

## 7. 图片发送与自动检测（核心功能）

这是后期新增的功能：用户发一张图片，系统自动调用 YOLO 检测，并把结果发回聊天室。

### 7.1 为什么图片不走 WebSocket

图片本体通过 HTTP 传输，而不是塞进 WebSocket 消息里。原因有三个：

1. **体积**：Base64 编码会让体积增大约 33%，而 WebSocket 单帧越大越容易造成卡顿甚至内存暴涨。
2. **一对多**：一张图要给房间里所有人看，用「URL + HTTP 缓存」比「给每个人推一份二进制」高效得多。
   图片文件名是随机且唯一的，内容永不改变，所以可以设置一年的强缓存。
3. **协议简洁**：WebSocket 只负责传 JSON 文本消息，逻辑清晰，不用处理二进制帧和文本帧混在一起的情况。

所以最终方案是：**WebSocket 传消息，HTTP 传文件**，两者共用 3000 端口。

### 7.2 为什么 YOLO 用常驻进程

ultralytics 加载权重、初始化 torch 大约需要 2~4 秒。
如果每检测一张图就起一个新进程，用户每发一张图都要多等好几秒，体验很差。

因此设计成**常驻进程**：进程只启动一次，模型只加载一次，
之后通过 stdin/stdout 按「一行一个 JSON」的方式反复收发请求，单张推理只要几毫秒到几十毫秒。

通信协议：

```text
启动成功  -> {"type":"ready","model":"...","classes":80}
启动失败  -> {"type":"fatal","error":"..."}

发送请求  -> {"id":1,"cmd":"detect","image":"C:\\...\\a.jpg","save_dir":"..."}
返回结果  -> {"id":1,"ok":true,"detections":[...],"annotated":"predict/a.jpg",...}
         或 {"id":1,"ok":false,"error":"..."}
```

设计上的两个细节：

- **日志走 stderr，协议走 stdout**。如果日志和 JSON 混在 stdout 里，Node 侧解析就会失败。
- **所有异常都在单条请求内部捕获**，转成 `{"ok":false}` 返回，主循环不会因为某张图片损坏而整个退出。

Node 侧还做了两件事保证健壮性：

- **请求排队（串行执行）**。YOLO 单张推理只要几十毫秒，串行的吞吐量完全够用；
  并发反而会让 CPU 争抢、内存暴涨。
- **进程崩溃后自动重启**。检测进程如果意外退出，状态会退回 `idle`，下次检测时自动重新拉起，不需要人工干预。

### 7.3 检测结果的完整流程

```text
用户选图
    ↓
前端先校验格式和大小（省一次无用上传）
    ↓
显示预览条，回车发送
    ↓
前端插入一条「临时消息」并显示本地上传进度（用户马上能看到图）
    ↓
HTTP POST /upload（图片原始字节）
    ↓
Node 按魔数校验真实格式 → 写入 uploads/original/
    ↓
存一条 type=image 的消息（status=pending）并广播
    ↓
HTTP 立刻返回回执（前端清掉临时消息，避免重复显示）
    ↓
Node 异步调用 Python 检测进程（不阻塞任何响应）
    ↓
Python 推理 + 保存画好框的图
    ↓
Node 把标注图移动到 uploads/annotated/
    ↓
① 回写原图片消息的 status=done 并广播（界面从「正在检测」变成「已检测到 N 个目标」）
② 新增一条 type=yolo 的消息并广播（标注图 + 类别标签 + 置信度）
```

**为什么拆成两条消息**：原图片消息用来表示「这张图检测完了」，YOLO 消息用来承载结果。
这样用户先看到自己发的图，几秒后检测结果再作为一条新消息出现，符合聊天室的直觉，
也不需要原地把一条消息改成一张完全不同的图片。

**为什么要先插临时消息**：否则用户选完图，在上传和检测的几秒里界面上什么都没有，
会以为没发出去。临时消息让整个等待过程可见（上传百分比 → 正在检测 → 已检测到 N 个目标）。

### 7.4 安全上的考虑

- **按魔数校验图片类型**，不看请求头里声明的 Content-Type。
  因为请求头是客户端说了算的，随时可以伪造；只看文件内容才可靠。
- **单张图片限制 10MB**，请求体超限直接断开，防止有人用超大文件把内存打满。
- **每个 IP 每分钟最多发 20 张图**，避免有人刷图把磁盘和 CPU 占满。
- **防目录穿越**：静态图片请求会把路径解析成绝对路径，
  再检查它是否仍然落在 `uploads/` 目录内，`../` 之类的路径会被拒绝。
- **前端渲染一律转义**。文本消息用 `textContent`，需要拼 HTML 的地方用统一的 `escapeHtml`，
  否则别人发一条带 `<script>` 的消息就能在所有人的页面上执行代码（XSS）。
- **文件名随机生成**（时间戳 + 随机串），避免不同房间、不同用户的图片重名互相覆盖。

### 7.5 边界情况的处理

| 情况 | 处理方式 |
| --- | --- |
| 服务器没装 ultralytics | 聊天和发图照常，图片下方显示「检测失败」，左侧栏提示 YOLO 不可用 |
| 找不到模型权重 | 按优先级在多个位置查找；都找不到时给出明确提示 |
| 发送时突然断网 | 图片进入等待队列，重新连上后自动补发，不用用户重选 |
| 图片格式不合法 | 前端先拦一道，后端再按魔数拦一道，返回 415 |
| 检测程序崩溃 | 自动重新拉起；本次检测返回失败消息，不影响下次 |
| 上传成功但广播还没到 | 前端用服务端回执里的正式消息补位，避免图片显示两次或长时间空白 |
| 3000 端口被占用 | 打印一句人话提示后正常退出，而不是抛出一大段堆栈 |

### 7.6 两个踩过的坑

**一、端口被占用时进程会崩**

`ws` 库有个容易忽略的行为：它会把宿主 HTTP 服务器的 `error` 事件
在 `WebSocketServer` 实例上再发一次。如果只给 http server 挂了监听，
端口冲突时仍然会抛出「未处理的 error 事件」，进程直接崩掉并打印长堆栈，
我们自己写的友好提示根本来不及显示。

解决办法是给 `server` 和 `wss` 都挂上同一个处理函数，并用一个标志位保证只执行一次。

**二、.bat 文件不能写中文**

cmd.exe 是按 OEM 代码页（中文 Windows 上是 GBK）**逐字节**读取 .bat 文件的。
如果文件保存为 UTF-8 而内容里有中文，那些多字节字符会被拆开误读，
`rem` 注释行和后面的命令都会被冲掉，脚本一启动就报一堆「不是内部或外部命令」然后退出，
表现出来就是「双击后窗口一闪就没了」。

所以 `start.bat`、`start_ai.bat`、`diagnose.bat` 全部保持纯 ASCII 英文，
中文说明一律放在 .md 文档里。

另外 .bat 里的延时统一用 `ping -n N 127.0.0.1 >nul` 而不是 `timeout /t N`，
因为 `timeout` 在 stdin 不是控制台时会直接报「不支持输入重新定向」并跳过等待。

## 8. 用户离开与连接关闭

当用户离开房间或者 WebSocket 连接关闭时，服务器会将该用户从对应房间的在线用户集合中移除，并进行相应的连接清理。

在线用户数据保存在内存中，因此服务器重启后当前房间和在线用户状态会被清空。

但是历史聊天记录保存在 SQLite 数据库中，因此服务器重新启动后，用户重新加入房间仍然可以获取之前保存的聊天记录。

关闭服务器时会先结束 Python 检测进程，避免在系统里留下孤儿进程。

---

## 9. 设计取舍

本项目定位为轻量级聊天室，因此没有引入复杂的分布式服务。

在线用户和房间状态使用 Node.js 内存保存，可以快速进行房间成员查找和消息广播。

聊天记录使用 SQLite 保存，SQLite 不需要单独部署数据库服务器，适合当前项目规模，同时可以满足聊天记录持久化的需求。

消息历史目前只加载最近 100 条，主要是为了限制单次查询和网络传输的数据量。

图片直接落盘而不是存数据库，是为了避免数据库体积膨胀，同时让浏览器能直接缓存图片。

YOLO 用「常驻子进程 + JSON 行协议」而不是「每次起新进程」或「独立 HTTP 微服务」：
前者太慢，后者对当前这个单机小项目来说又太重（要额外管理端口、进程和跨域），
子进程 + 标准输入输出的方案在「够快」和「够简单」之间比较平衡。

---

## 10. 当前已知问题

目前项目仍然属于轻量级聊天室实现，存在以下限制：

1. 当前没有完整的用户账号和密码认证机制，用户身份主要通过昵称识别。
2. 客户端提交的信息仍然存在被伪造的可能。图片上传接口的房间名和昵称来自 URL 参数，
   没有和已建立的 WebSocket 连接做绑定，理论上可以冒充别人的昵称发图。
3. 在线用户和房间状态保存在 Node.js 内存中，服务器重启后会丢失。
4. 当前历史消息默认只加载最近 100 条。
5. 项目目前主要针对小规模聊天室设计，没有针对大规模并发场景进行专门优化。
6. 上传的图片和标注图会一直留在 `uploads/` 目录里，目前没有自动清理机制，长期使用需要手动清理。
7. 检测请求是串行的。多人同时发图时，后面的请求要排队等待；
   在单机单卡的情况下这是有意为之（避免资源争抢），但如果并发量真的很大需要改成批量推理。
8. 模型是 COCO 80 类，只能识别这 80 种常见目标，识别不出来时会显示「没有检测到目标」。
