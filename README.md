# yolo-chat

含两部分：

| 目录 | 内容 | 技术栈 |
| --- | --- | --- |
| [`chat/`](chat/) | 多人聊天室 + YOLO 自动检测接入 | Node.js（ws + better-sqlite3）/ 原生前端 / Python |
| [`train/`](train/) | YOLO 模型训练与推理脚本 | Python（ultralytics / PyTorch） |

两部分通过「Python 常驻子进程 + JSON 行协议」连接，详见下面的[两个项目是怎么连起来的](#两个项目是怎么连起来的)。

## 快速开始

### 1. 环境要求

| 需要 | 版本 | 用途 |
| --- | --- | --- |
| Node.js | 18 以上 | 聊天室后端（聊天 / 图片上传 / 图片访问） |
| Python | 3.10 以上 | 前端静态服务器 + YOLO 检测 |
| ultralytics | 最新 | 目标检测 |

```bat
node -v
py --version
py -m pip install ultralytics
```

### 2. 准备模型权重（重要）

**本仓库不包含训练好的模型权重。** 所以刚克隆下来时，聊天和发图都能正常用，
但图片下方会显示「检测失败」，因为找不到 `best.pt`。

需要先跑一遍训练把它生成出来：

```bat
cd train
python train.py
```

训练完成后权重会出现在 `train/runs/detect/train-2/weights/best.pt`，
`chat/` 会自动找到它，不需要任何配置。

> 为什么仓库不带权重？见下面的[设计取舍](#设计取舍)。


```bat
set YOLO_MODEL=D:\somewhere\best.pt
```

### 3. 启动

```bat
cd chat
start_ai.bat
```

它会启动后端和前端，并自动打开 <http://localhost:8080/index.html>。

也可以手动分两个窗口：

```bat
cd chat
npm install
node server.js
```

```bat
cd chat
py -m http.server 8080
```

### 4. 使用

1. 输入昵称和房间名，加入房间
2. 点输入框左边的 🖼 选图，或者直接把图片拖进聊天区，也可以按 Ctrl+V 粘贴
3. 回车发送
4. 图片立刻出现（先显示上传进度，再显示「正在检测…」）
5. 几秒内 YOLO 会发出一条消息，包含**画好检测框的图片**和**类别 + 置信度**列表

## 两个项目是怎么连起来的

### 整体数据流

```text
浏览器
  │
  ├── WebSocket ────► 文本消息 / 图片消息 / 检测结果     （端口 3000）
  ├── HTTP POST ────► 上传图片本体                        （端口 3000）
  └── HTTP GET ─────► 读取原图和标注图                   （端口 3000）
                              │
                              ▼
                       Node.js 后端（chat/server.js）
                              │
                              ├── 内存：在线用户、房间、连接
                              ├── SQLite：聊天记录
                              │
                              └── stdin/stdout，一行一个 JSON
                                        │
                                        ▼
                              Python 常驻进程（chat/yolo_worker.py）
                                        │
                                        ▼
                              train/ 训练出来的 best.pt
```

发一张图的完整过程：

```text
用户选图
   ↓
前端先校验格式和大小（省一次无用上传）
   ↓
插入「临时消息」显示本地上传进度（用户马上能看到图）
   ↓
HTTP POST /upload 上传图片原始字节
   ↓
按魔数校验真实格式 → 写入 uploads/original/
   ↓
存一条 type=image 的消息（status=pending）并广播
   ↓
立刻返回回执（前端清掉临时消息，避免重复显示）
   ↓
异步调用 Python 检测进程（不阻塞任何响应）
   ↓
Python 用 train/ 的 best.pt 推理 + 保存画好框的图
   ↓
① 回写原图片消息 status=done 并广播（「正在检测」→「已检测到 N 个目标」）
② 新增一条 type=yolo 的消息并广播（标注图 + 类别标签 + 置信度）
```

### 三个关键设计决定

**一、图片走 HTTP，不走 WebSocket。**
Base64 会让体积增大约 33%，而一张图要给整个房间的人看，
用「随机文件名 + URL + 一年强缓存」比给每个人推一份二进制高效得多。
WebSocket 只负责传 JSON 消息，协议保持简单。

**二、YOLO 用常驻进程，不是每次起新进程。**
ultralytics 加载权重、初始化 torch 要 2~4 秒，而单张推理只要 6~30 毫秒。
如果每张图都重新起进程，用户每次都要多等好几秒。
现在进程只启动一次，通过 stdin/stdout 按「一行一个 JSON」反复收发。
日志走 stderr、协议走 stdout，两者不能混。

**三、检测进程崩溃能自愈。**
定期心跳检查，进程挂了会在 5 秒后自动重启；
启动失败也会在冷却 30 秒后重试，不需要人工干预。
每次启动/崩溃的原因都写在日志里，`chat/diagnose.bat` 能一次收集齐。

## 设计取舍

### 为什么仓库不带模型权重

`best.pt` 是训练产物，单个约 5.3MB。仓库只保留源码，理由：

1. **它是可再生的。** 跑一遍 `train/train.py` 就能得到，不需要版本化管理二进制文件。
2. **避免仓库随训练次数膨胀。** 每换一次超参数就多一个权重文件，Git 对二进制文件的差异存储效率很低，仓库会迅速变大。
3. **作业本身要能体现训练过程。** `train/` 里的脚本 + 数据集说明足以复现结果，这比直接塞一个权重文件更能说明问题。

代价是克隆后必须先训练一次才能用自动检测功能，这一点已在
[准备模型权重](#2-准备模型权重重要)里明确说明，并且代码做了优雅降级：
找不到权重时聊天和发图照常可用，只是提示检测不可用。

如果以后确实需要把权重一起发布，用 Git LFS 是更合适的做法
（`git lfs track "*.pt"`），而不是直接提交进普通 Git 历史。

### 其他取舍

- **图片存文件系统而不是数据库。** 数据库适合结构化数据，把几 MB 的二进制塞进去会让库迅速膨胀、备份变慢；图片本来就能通过 URL 让浏览器直接缓存。
- **消息内容用 JSON 存在 `content` 字段里。** 只需给老表加一个 `type` 列就能完成升级，旧的文本消息完全不受影响（`type` 默认就是 `text`），不用重建表。
- **检测请求串行执行。** 单张推理只要几十毫秒，串行吞吐量足够；并发反而会让 CPU/GPU 争抢资源。
- **聊天记录用 SQLite。** 不需要单独部署数据库服务器，适合这个项目规模。

## 已知问题

1. 没有完整的用户账号和密码认证机制，身份主要靠昵称识别。
2. 图片上传接口的房间名和昵称来自 URL 参数，没有和已建立的 WebSocket 连接绑定，理论上可以冒充别人昵称发图。
3. 在线用户和房间状态存在 Node.js 内存里，服务器重启后会丢失（聊天记录不受影响）。
4. 历史消息默认只加载最近 100 条，获取更多历史的功能还没做。
5. `chat/uploads/` 里的图片会一直保留，没有自动清理机制，长期使用需要手动清理。
6. 检测请求串行，多人同时发图时后面的要排队（单机单卡下这是有意为之）。
7. 模型是 COCO 80 类，只能识别这 80 种常见目标。
